# 长会话容量验收

2026-09-09，在 Windows / Python 3.12 的同一主机上完成 1、4、8 会话三组运行。
每组使用全新子进程，每会话 4096 根确认，每根 4 次 preview，retention=64、
max_bars=256、请求缓存/输出预算=2048。会话顺序轮转，不是八线程并行计算。

**结论：本组固定负载的有界长会话验收通过，可作为受控嵌入的容量起点。**
这不是任意脚本、真实 provider、跨主机或长期墙钟服务的容量保证；没有据此增加
默认并发、放宽性能阈值或新增运行时优化。

## 已核对的结果

共 266,240 次计时事件、48 个进程采样窗口、1540 项适用检查，未发现不变量失败或
悬而未决的恢复延续检查。维护者从 JSONL 独立复算事件数、每根 preview/commit
计数、窗口 median/p95/max，并核对最终检查状态；不只信任报告的 completed 标记。

| --- | --- | --- | --- | --- | --- |
| 1 | 1 / 0 / 0 | 43.69 → 45.98 | 11.83 / 15.19 | 7.55 / 9.99 | 7 |

耗时是该组混合事件的描述统计。负载占比不同，不能从 median 下降推导增加会话会
提速。最大 preview 为 81.94 ms，最大确认 74.57 ms；主机同时进行普通开发工作，
不是空闲隔离实验室，也没有把这些数值升级为生产 SLA。计时不含文件写入和窗口检查。

RSS 为 Windows WorkingSetSize，包含解释器、provider、会话、分配器保留及窗口
报告。原始样本只写 JSONL，但少量窗口摘要随窗口数增长，因此末端增量不能直接
归因为运行时泄漏。观察到窗口内缓存条目下降与 fetches 增加，是缓存再取数证据的
下界；不是精确淘汰次数。4096 根覆盖 64 次 retention 窗口长度。

每个窗口检查已提交恢复结果，恢复体的下一根输出与尚未恢复的原会话下一次真实确认
比较；末窗口另作一根非计时确认。preview 与旧绘图点保留检查作用于每窗口首根实际
事件，完整逐根语义覆盖仍由代表性脚本测试负责。循环策略持续交易：持仓符合其周期，
完整周期采样点的净收益和手续费有独立算术检查，不使用长期闲置策略冒充持续交易。
