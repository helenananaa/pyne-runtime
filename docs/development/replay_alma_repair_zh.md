# 策略回放拆分与 ALMA 指数分带

候选 `0.4.1rc38`，计算语义仍为 `42`。本轮继续处理 rc37 验收记录中
留下的策略回放结构债务和极端动态范围 ALMA 成本。历史 rc37 的验收记录
保留在 [加权计算与状态修复](weighted_state_audit_repair_zh.md)。

## 策略回放

原 `replay_strategy_orders` 共 701 行，持有成交、持仓、风险和交易历史等
闭包状态。现在主函数只协调每根 bar 的执行阶段：会话风险重置、结转挂单、
计算阶段可见状态、当前订单、当前挂单、强平、结果写入、bar 末风险锁定。

- `replay_state.py` 声明瞬态持仓与风险状态，并集中绑定策略所有者提供的
  数据、成本计算、保证金准入和操作预算；这些对象不进入快照。
- `replay_events.py` 处理原始订单重置、时间调度、准入与取消。
- `replay_fills.py` 处理挂单触发、成交准备和提交，以及市场单和减仓。
- `replay_risk.py` 处理会话重置、风险强平和权益锁定。
- `replay_output.py` 写入权益/持仓数组并发布交易报告。
- `replay_values.py` 保留值规范化和持仓计算辅助函数。

分解保留市场单与挂单原有的准入、运算和舍入顺序。收盘成交模式仍先处理
结转订单，发布计算阶段可见状态，再处理当根提交的订单；动态减仓仍读取
正确的可见持仓。操作预算继续累计，风险生成单仍在回放时重新推导。
原性能测试只调整计数探针所在模块，保留实际回放次数、写入次数、线性
存储和未触发挂单的零触发计算断言。

## ALMA 精确计算

原无进位整数多项式算法在同时出现 `1e308` 与 `1e-300` 时，为每个系数
保留约两千位跨度。新的实现按有效尾指数划分窄带。binary64 的有效数字
最多 53 位，以 53 位为带宽可将带内整数控制在 106 位以内；各带分别做
无进位整数卷积，用整数左移合并，最后只舍入一次。

普通窄跨度数据继续使用单次整数乘法。选择器比较稠密、单侧分带和双侧
分带，估算每对的带进位保护字节宽度，并至少计入一个 binary64 有效数字
所需的 7 字节处理开销。只有组合估算小于原稠密宽度时才分带，避免很多
低有效位整数被低估，从而产生过多轮 Python 编码和解码。
窗口 2 直接使用固定两项的精确表达式，避免规划开销。窗口不超过 32 时
还要求两倍的估算压缩余量，并在稠密宽度已经较小时提前跳过分带规划。
两条路径都保持有符号补偿、次正规数、消减与溢出行为，不使用浮点 FFT。
追加未来值即使改变算法选择，也不会改变已完成窗口。

收尾复核曾确认 39 个源带 × 3 个权重带的 117 对组合反例：10k 数据、
窗口 32 的初版约为旧版的 3.24 倍耗时。修正开销估算后采用稠密路径，
恢复到旧版相当的耗时；原始慢路径记录与修复后对照均保留，未坚持初版
算法选择断言，也未改数值参考或容差。
短窗口准入邻界也确认过 1.5～1.9 倍退化；窗口 2 的固定表达式及窗口
3／7／32 的开销余量消除了这些实测退化，并保留极端跨度的收益。

最终源码冻结后，对三类输入分别测量 10k／20k／40k 数据、窗口 1000，
每个版本和场景使用新进程，运行三次并排除预热。耗时测量不开启
`tracemalloc`，之后在同一进程单独开启内存跟踪。这些测量针对
`exact_convolution` ALMA 卷积核心，权重在计时前准备，未包含公开 ALMA
接口或 Pyne 执行器的端到端成本。以下为 40k 样例的耗时中位数，全部九组
输出的 binary64 位模式与 rc37 一致。

| 输入 | rc37 | rc38 | 比值 |
| --- | ---: | ---: | ---: |
| 普通带符号数值 | 0.21355 秒 | 0.21443 秒 | 耗时增加 0.41% |
| 极端动态范围、含正负抵消 | 10.07821 秒 | 0.43128 秒 | 加速 23.37 倍 |
| 多种指数尺度、含正负抵消 | 13.42649 秒 | 1.40696 秒 | 加速 9.54 倍 |

普通 10k／20k／40k 样例耗时变化分别为 −3.8%／−0.15%／+0.41%。
最终改动只影响短窗口规划，1000 窗口的旧版数据复用已保留的真实 rc37
测量；最终新版样本重新运行。收据 `baselineReuse` 标明旧记录哈希和写入
时间，旧样本只记录单调时钟耗时，没有补造每次采样的 UTC 时间。

内存并非全面下降。40k 极端／多尺度样例的 Python 跟踪分配峰值分别从
32.69／32.45 MiB 降到 29.87／28.19 MiB；新进程的峰值 working set 却
从 76.51／79.23 MiB 升到 88.86／89.37 MiB，增加约 12.36／10.14 MiB。
进程峰值包含导入、预热、数值运算和分配器保留，不能用跟踪分配量替代。
普通数据跟踪峰值仅多 120 字节，进程峰值相当。更大规模的常驻内存上限
未在本轮资格范围内。

策略回放保留原来的 23 项工作量与存储回归断言。另以无订单、密集市场单、
收盘成交和未触发挂单四类场景，分别运行 1k／2k／4k 数据、九次采样；
12 组结果哈希均与 rc37 相同。顺序执行的两版墙钟耗时受到机器运行阶段
影响，不将它们作为重构带来吞吐收益的依据。

原始对照、已确认的慢路径反例与最终验收记录位于
`.tmp/audit-replay-alma-20261004/`，包括 `numeric/paired-performance.json`、
`numeric/adjacent-short-probe.json` 和 `strategy-performance-current-final.json`。

## 快照与交付边界

本轮是保持计算结果和状态契约的重构与优化，没有升级计算语义。真实 rc37
wheel 导出的语义 42 state/replay 保留在 `tests/golden/replay_alma_semantics_v42`，
包括 wheel 来源哈希、脚本、数据、快照和结果哈希。新运行时必须直接恢复、隔离 preview
并继续执行；没有重标记旧快照。更早的语义 41 快照仍按原规则拒绝并重建。

极宽且密集的指数分布仍可能采用原精确整数路径；并未将任意规模输入的
耗时或 RSS 视为已验收。有限状态配额下的嵌套变异重新计量等其他已披露
边界保留。验收时工作为本地候选改动，尚未 commit、push 或发布；
后续本地交付以 Git 提交记录为准。
